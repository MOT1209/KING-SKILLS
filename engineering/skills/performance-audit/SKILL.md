# تدقيق الأداء

## متى تُستخدم
- المستخدم يشكو من بطء نقطة API أو صفحة أو استعلام أو مهمة.
- قبل تحسين مبكر لا يستند إلى قياس.
- التحقق من أن تحسيناً فعلاً حسّن الأداء.

لا تُستخدم عندما: لا توجد شكوى أداء ولا قياس (مراجعة عامة: `code-review`)، أو المطلوب تحسين استباقي بلا قياس.

## خطوات العمل
1. عرّف المشكلة بمقياس قابل للقياس: ما العملية، وما الزمن أو الاستهلاك الحالي، وما الهدف الذي يحدده المستخدم. لا تفترض هدفاً.
2. أعد إنتاج البطء في ظروف ثابتة (بيانات، بيئة، تشغيلات متعددة) وسجّل خط الأساس بأداة قياس مناسبة (profiler، `EXPLAIN` للاستعلامات، سجلات التوقيت).
3. حدّد عنق الزجاجة بالقياس لا بالتخمين: وحدة المعالجة، الذاكرة، الإدخال/الإخراج، الشبكة، قاعدة البيانات، أو الأقفال.
4. ابحث عن الأسباب الشائعة: استعلامات متكررة (N+1)، غياب فهرس، جلب أعمدة وصفوف زائدة، حلقات متداخلة، عمل متكرر يمكن تخزينه، عمليات متزامنة يمكن تجميعها أو توازيها، تخصيص ذاكرة مفرط.
5. اقترح تحسينات مرتبة بنسبة الأثر المتوقع إلى التعقيد، وجرّب واحداً في كل مرة.
6. بعد كل تعديل أعد القياس بالطريقة نفسها وقارن بخط الأساس. احتفظ بالتعديل فقط إن تحسّن الأداء بوضوح وبقي السلوك صحيحاً (شغّل الاختبارات).
7. تحقق من الآثار الجانبية: زيادة استهلاك الذاكرة، بيانات قديمة في التخزين المؤقت، تعقيد الصيانة.
8. دوّن النتائج: قبل/بعد، ما جُرّب وما أُهمل، وما يحتاج مراقبة في الإنتاج.

## صيغة المخرجات
ملخص المشكلة والهدف، جدول قياسات (خط الأساس، بعد كل تعديل)، التشخيص مع الدليل، التعديلات المطبقة، المخاطر، وتوصيات المتابعة.

## قواعد وحدود
- لا تدّعِ تحسناً دون قياس قبل وبعد بالطريقة نفسها؛ لا تختلق أرقاماً.
- لا تحسّن شيئاً لم يثبت أنه عنق زجاجة.
- لا تضحّ بالصحة أو القراءة مقابل مكسب هامشي.
- لا تشغّل اختبارات حِمل على بيئة إنتاج دون إذن صريح.
- القياس على جهاز التطوير لا يطابق الإنتاج؛ اذكر ذلك.

## قائمة تحقق
- الهدف والمقياس معرَّفان قبل أي تعديل.
- خط الأساس مسجَّل بتشغيلات متعددة.
- التعديل الواحد يُقاس منفرداً.
- الاختبارات تمر بعد التحسين والمخرجات متطابقة.
- الآثار الجانبية (ذاكرة، بيانات قديمة) فُحصت.

## حالات حدّية
- تذبذب كبير بين التشغيلات: كرّر القياس واذكر المدى لا قيمة واحدة.
- البطء يظهر فقط مع حجم بيانات كبير: أنشئ بيانات اختبار اصطناعية بحجم مناسب (لا حقيقية).
- التحسين يتطلب تغيير مخطط القاعدة: مرّر الأمر عبر `db-schema-design` وخطة ترحيل.
- مصدر البطء خدمة خارجية: اقترح مهلات وتخزيناً مؤقتاً وتوازياً بدل تحسين الكود المحلي.
- تحسين يرفع استهلاك الذاكرة بوضوح: اعرض المقايضة واترك القرار للمستخدم.

## مثال كامل
### المدخل
«نقطة `GET /orders` بطيئة. تجلب الطلبات ثم تستعلم عن عميل كل طلب. لا أعرف الأرقام.»

### المخرج
```
خط الأساس (20 تشغيلاً، بيانات اختبار اصطناعية): [يُقاس: متوسط ومدى]. عدد الاستعلامات للطلب الواحد: 1 + N.
التشخيص: نمط N+1 — استعلام العميل داخل حلقة (orders.service.ts).
التعديل: جلب العملاء دفعة واحدة بـ WHERE id IN (...) وربطهم في الذاكرة.
بعد التعديل: أعد القياس بالطريقة نفسها: [يُقاس]. عدد الاستعلامات: 2.
التحقق: اختبارات النقطة تمر، والمخرجات متطابقة.
مخاطر: قائمة id كبيرة قد تتطلب تجزئة. متابعة: فهرس على orders.customer_id إن لم يوجد.
```
(الأرقام المحلية تُملأ من قياساتك الفعلية؛ لا أقدّم أرقاماً لم تُقَس.)
