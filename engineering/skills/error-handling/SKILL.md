# معالجة الأخطاء

## متى تُستخدم
- تصميم استراتيجية أخطاء لخدمة جديدة أو توحيدها في مشروع قائم.
- مراجعة كود فيه `catch` فارغ أو رسائل غامضة أو أخطاء تتسرّب للمستخدم.
- ربط الأخطاء بالتسجيل وأكواد الاستجابة.

لا تُستخدم عندما: المطلوب تحليل خطأ وقع فعلاً من سجلاته (`debug-logs`).

## خطوات العمل
1. اقرأ كيف تُعالَج الأخطاء الآن: نقاط الدخول، الوسائط (middleware)، الطبقات (واجهة، خدمة، بيانات)، ومكتبة التسجيل المستخدمة.
2. صنّف الأخطاء: أخطاء تحقق من المدخلات، أخطاء أعمال متوقعة، أخطاء اعتماديات خارجية (قابلة لإعادة المحاولة)، أخطاء برمجية غير متوقعة.
3. عرّف تسلسلاً هرمياً للأخطاء أو أكواداً آلية ثابتة (`code`) مستقلة عن الرسالة النصية.
4. حدّد قاعدة الطبقات: كل طبقة تلتقط ما تفهمه وتحوّله أو تغلّفه مع الحفاظ على السبب الأصلي (cause)، ولا تبتلع الأخطاء، ولا تلتقط ثم تعيد الرمي بلا إضافة سياق.
5. افصل الرسالة للمستخدم عن التفاصيل التقنية: رسالة آمنة وواضحة للمستخدم، والتفاصيل في السجل فقط.
6. اضبط التسجيل: مستوى مناسب لكل نوع، تسجيل الخطأ مرة واحدة عند الحدّ الخارجي لتفادي التكرار، مع سياق منظم (معرّف الطلب، المستخدم المجهَّل، العملية).
7. حدّد سياسة إعادة المحاولة للأعطال العابرة: عدد محدود، تأخير متصاعد، وفقط للعمليات الآمنة التكرار.
8. اختبر مسارات الفشل: اختبار لكل نوع خطأ رئيس ولتحويل الأخطاء بين الطبقات.

## صيغة المخرجات
جدول تصنيف الأخطاء (النوع، الكود، رمز الاستجابة، رسالة المستخدم، مستوى السجل، إعادة المحاولة)، ثم الكود النموذجي للطبقات، ثم قائمة تعديلات المواضع الضعيفة.

## قواعد وحدود
- لا تسجّل كلمات مرور أو رموزاً أو بيانات شخصية أو أسراراً في السجلات أو الرسائل.
- لا تعرض Stack Trace أو تفاصيل الاستعلامات للمستخدم النهائي.
- لا تستعمل `catch` فارغاً؛ إن كان التجاهل مقصوداً فوثّق السبب.
- لا تستخدم الاستثناءات للتحكم بالتدفق الطبيعي.
- لا تغيّر رموز استجابة موجودة دون إبلاغ المستهلكين.

## حالات حدّية
- عمل غير متزامن (Promise/async): تأكد أن الرفض يُلتقط ولا يضيع.
- فشل جزئي في عملية دفعية: عالج كل عنصر وأرجع تقرير نجاح/فشل بدل الفشل الكلي إن ناسب.
- فشل أثناء التنظيف (finally): لا تُخفِ الخطأ الأصلي.
- مهمة خلفية بلا مستخدم: سجّل وتنبيه بدل رسالة للمستخدم.
- الخيار `cause` في `new Error(message, { cause })` يتطلب بيئة تشغيل ومكتبات أنواع تدعم ES2022؛ تحقق من `target`/`lib` في المشروع وإلا مرّر السبب كحقل خاص.

## مثال كامل
### المدخل
```ts
try { await db.save(order); } catch (e) { console.log(e); return { ok: false }; }
```
### المخرج
```ts
class AppError extends Error {
  constructor(readonly code: string, message: string, options?: { cause?: unknown }) {
    super(message, options);
  }
}

try {
  await db.save(order);
} catch (err) {
  logger.error({ err, requestId, orderId: order.id }, "order_save_failed");
  throw new AppError("ORDER_SAVE_FAILED", "Could not save the order", { cause: err });
}
// عند الحدّ الخارجي: AppError → استجابة 500 برسالة آمنة + request_id، دون تسريب err.
```
التعديلات: `console.log` ← سجل منظم، إعادة رمي بسياق وسبب أصلي بدل نتيجة `ok:false` تُخفي الفشل. سؤال: أي أخطاء قاعدة البيانات قابلة لإعادة المحاولة عندكم؟
