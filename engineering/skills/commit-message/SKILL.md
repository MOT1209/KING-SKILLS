# رسائل Commit

## متى تُستخدم
- كتابة رسالة commit لتغيير جاهز.
- تحسين رسائل غامضة مثل «fix stuff» أو «update».
- تقسيم تغيير كبير إلى commits منطقية.

لا تُستخدم عندما: المطلوب وصف طلب دمج كامل (`pr-description`).

## خطوات العمل
1. اقرأ التغييرات الفعلية (`git diff --staged` أو ما يكافئه) ولا تكتب الرسالة من أسماء الملفات.
2. افحص سجل المستودع القريب لتعرف الأعراف المتبعة (اللغة، النطاقات، الصيغة)، والتزم بها.
3. اتبع مواصفة Conventional Commits 1.0.0: `type(scope)!: description`، ثم سطر فارغ ثم جسم اختياري ثم تذييلات اختيارية.
4. اختر النوع: `feat` لميزة جديدة، `fix` لإصلاح خطأ (هذان من المواصفة نفسها)، وأنواع شائعة أخرى معتمدة بالعرف (مثل `docs`، `refactor`، `perf`، `test`، `build`، `ci`، `chore`، `style`) إن كان المستودع يستعملها.
5. اكتب الوصف بصيغة الأمر أو المضارع المباشر، موجزاً، بلا نقطة في النهاية، ويُفضَّل عرفاً ألا يتجاوز نحو 72 حرفاً.
6. اشرح في الجسم «لماذا» لا «ماذا» فقط، إن لم يكن السبب واضحاً من الوصف.
7. للتغيير الكاسر ضع `!` بعد النوع/النطاق و/أو تذييل `BREAKING CHANGE: ...` يصف الأثر وطريقة الترحيل.
8. اربط المهام في التذييل إن كان المستودع يستعمل ذلك (مثل `Refs: ORD-123`).
9. إن كان التغيير يخلط أمرين مختلفين فاقترح تقسيمه إلى commits.

## صيغة المخرجات
```
<type>(<scope>)<!>: <description>

<body: لماذا + ملاحظات>

<footer: BREAKING CHANGE / Refs>
```
وإن طُلب عدة خيارات فقدّم خياراً أساسياً وبديلاً واحداً.

## قواعد وحدود
- لا تصف ما لم يتغير فعلاً.
- لا تضع أسراراً أو بيانات شخصية في الرسالة.
- لا تستخدم `fix` لتغيير سلوك مقصود جديد ولا `feat` لتنظيف داخلي.
- لا تدمج أنواعاً متعددة في رسالة واحدة؛ اقسم التغيير.
- التزم لغة المستودع (إنجليزية غالباً)؛ اسأل إن لم يتضح.

## قائمة تحقق
- الرسالة تصف التغيير الفعلي.
- النوع صحيح، والنطاق موافق لأعراف المستودع.
- الكاسر موسوم صراحة.

## حالات حدّية
- commit يمسّ نطاقات متعددة: احذف النطاق أو اقسم الـ commit.
- إلغاء commit سابق: استخدم `revert:` أو صيغة git الافتراضية مع الإشارة إلى المعرّف.
- تغيير بلا سبب واضح: اسأل عن السبب بدل تخمينه.
- commit تجريبي مؤقت (WIP): اقترح عدم دفعه كما هو وضمّه قبل الدمج.

## مثال كامل
### المدخل
تغيير في `orders.service.ts` يمنع إلغاء الطلبات المشحونة، مع اختبارين، ويرجع 409 بدل 200. المهمة ORD-123.

### المخرج
```
fix(orders): reject cancellation of shipped orders

Cancelling a shipped order previously returned 200 and left the order in an
inconsistent state. Return 409 Conflict for any status other than pending or paid.

Refs: ORD-123
```
البديل (إن كان السلوك الجديد يكسر عملاء يعتمدون على 200):
```
fix(orders)!: return 409 when cancelling shipped orders

BREAKING CHANGE: POST /orders/{id}/cancellation now returns 409 for shipped orders instead of 200.
```
