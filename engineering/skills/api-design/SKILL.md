# تصميم واجهات API

## متى تُستخدم
- تصميم واجهة جديدة أو توسيع واجهة قائمة.
- مراجعة تناسق واجهة تضخمت بلا قواعد.
- تحديد صيغة الأخطاء والإصدارات.

لا تُستخدم عندما: المطلوب تصميم جداول القاعدة (`db-schema-design`) أو توثيق واجهة موجودة فقط (`technical-docs`).

## خطوات العمل
1. حدّد المستهلكين (واجهة ويب، جوال، خدمات) والموارد الأساسية وعلاقاتها. إن وُجدت واجهات قائمة فاقرأها والتزم بأعرافها.
2. اختر النمط: REST للموارد والعمليات القياسية، وGraphQL حين يحتاج العملاء إلى تشكيل البيانات بمرونة؛ اذكر السبب.
3. في REST: أسماء موارد بصيغة الجمع (`/orders`)، الفعل من طريقة HTTP، علاقات متداخلة بعمق معقول (`/orders/{id}/items`)، وأسماء حقول بنمط واحد (snake_case أو camelCase).
4. استخدم رموز الحالة بحسب RFC 9110 (مثل 200، 201، 204، 400، 401، 403، 404، 409، 422، 429)، واختر واحداً لكل حالة وثبّته.
5. وحّد صيغة الأخطاء؛ يُفضَّل Problem Details for HTTP APIs (RFC 9457) أو صيغة داخلية ثابتة تضم: `code` آلياً، و`message`، و`details`، و`request_id`.
6. صمّم الترقيم (pagination)، الفرز، والتصفية بصيغة موحدة، وحدد حدّ الصفحة كقيمة قابلة للضبط.
7. للتعديلات التي تُعاد محاولتها (الدفع مثلاً) فكّر بمفتاح تكرار آمن (Idempotency Key).
8. حدّد استراتيجية الإصدار (مسار `/v1` أو ترويسة)، وما يُعدّ تغييراً كاسراً، وسياسة الإيقاف.
9. في GraphQL: صمّم المخطط (Schema) من احتياجات العملاء، وسمِّ الأنواع والحقول بوضوح، واستخدم أنواع الإدخال (Input Types)، وصمّم أخطاء الأعمال داخل الاستجابة بنمط ثابت، وانتبه لمشكلة الاستعلامات المتداخلة (N+1) وإلى حدود عمق الاستعلام وتعقيده.
10. حدّد المصادقة والتفويض لكل نقطة: من يستطيع ماذا، وما الذي يُرجَع لكل دور.
11. اعرض المخطط بصيغة OpenAPI أو جدول، مع أمثلة طلب واستجابة.

## صيغة المخرجات
جدول النقاط (الطريقة، المسار، الغرض، الحالات الناجحة، الأخطاء)، ثم نماذج الطلب والاستجابة، ثم قسم للأخطاء والإصدار، ثم قرارات مفتوحة.

## قواعد وحدود
- لا تكشف معرّفات داخلية تسرّب بنية القاعدة إن أمكن؛ فكّر بمعرّفات غير متسلسلة.
- لا تضع أسراراً أو رموزاً حقيقية في الأمثلة.
- لا تغيّر معنى حقل موجود داخل الإصدار نفسه.
- لا تقدّم حدوداً رقمية (معدل الطلبات، حجم الصفحة) كمعيار؛ هي قرارات المشروع.

## حالات حدّية
- عمليات ليست CRUD (مثل «إلغاء الطلب»): استخدم مورداً فرعياً أو حدثاً (`POST /orders/{id}/cancellation`) وثبّت النمط.
- حذف مورد مرتبط بغيره: حدّد 409 أو حذفاً متتالياً بقرار صريح.
- الحقول الحساسة: لا تُرجَع افتراضياً.
- طلب كبير الحجم (رفع ملفات): استخدم مساراً مخصصاً ورابط رفع مؤقتاً بدل تضمينه في JSON.
- التزامن (تعديل متزامن لمورد): فكّر بـ `ETag`/`If-Match` أو رقم نسخة، وأرجع 409 أو 412 بقرار ثابت.

## مثال كامل
### المدخل
«صمّم واجهة REST لإدارة الطلبات: إنشاء، عرض، إلغاء، مع قائمة قابلة للتصفية.»

### المخرج
| الطريقة | المسار | الغرض | النجاح | الأخطاء |
|---|---|---|---|---|
| POST | /v1/orders | إنشاء طلب | 201 | 400، 422 |
| GET | /v1/orders | قائمة (`?status=&cursor=&limit=`) | 200 | 400 |
| GET | /v1/orders/{id} | تفاصيل | 200 | 404 |
| POST | /v1/orders/{id}/cancellation | إلغاء | 200 | 404، 409 |

```
POST /v1/orders  { "customer_id": "cus_example", "items": [{ "sku": "SKU-1", "qty": 2 }] }
201 { "id": "ord_example", "status": "pending" }

409 { "code": "order_not_cancellable", "message": "Order already shipped", "request_id": "req_example" }
```
الإصدار: المسار `/v1`، والتغيير الكاسر يُنشر في `/v2`. سؤال مفتوح: هل يلزم مفتاح تكرار لـ POST /orders؟
