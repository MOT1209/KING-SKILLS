# إعادة إنتاج الأخطاء

## متى تُستخدم
- تقرير خطأ غامض أو غير قابل للتكرار.
- قبل إصلاح خطأ: تريد إثبات وجوده وحماية المستقبل من عودته.
- تحويل بلاغ مستخدم إلى حالة اختبار.

لا تُستخدم عندما: المطلوب تحديد سبب خطأ إنتاج من السجلات (`debug-logs`)، أو إصلاح الخطأ نفسه.

## خطوات العمل
1. اجمع المعلومات: ما الحاصل، وما المتوقع، البيئة والإصدار، المدخلات، السجلات، رسائل الخطأ، وتكرار الحدوث.
2. اقرأ الشيفرة ذات الصلة وحدّد الفرضيات المحتملة للسبب، مرتبة بالاحتمال.
3. أعد الإنتاج بأبسط خطوات ممكنة: ابدأ من البلاغ الأصلي ثم احذف كل ما لا يلزم حتى يبقى الحد الأدنى الذي يعيد الخطأ.
4. اكتب خطوات الإعادة مرقمة: الحالة الأولية، الأوامر أو الإجراءات، النتيجة الفعلية، النتيجة المتوقعة.
5. اكتب اختباراً آلياً يفشل بسبب الخطأ نفسه (لا بسبب خطأ في الاختبار)، في أدنى مستوى يمكن إظهاره فيه (وحدة قبل تكامل قبل E2E).
6. شغّل الاختبار وتأكد أن الفشل بالرسالة المتوقعة، وأرفق المخرجات.
7. إن لم تستطع إعادة الإنتاج: دوّن ما جرّبته، وما ينقصك (بيانات، إصدار، سجلات)، واقترح تسجيلاً إضافياً.
8. لا تُصلح الخطأ ضمن هذه المهارة ما لم يُطلب؛ سلّم الاختبار الفاشل للخطوة التالية (الإصلاح)، وبعد الإصلاح يجب أن ينجح الاختبار نفسه.

## صيغة المخرجات
```
# إعادة إنتاج: <عنوان>
البيئة / الإصدار:
الخطوات: 1..n
الفعلي:   المتوقع:
الحد الأدنى للمدخلات:
الاختبار الفاشل: <كود + مخرجات التشغيل>
فرضيات السبب: مرتبة
```

## قواعد وحدود
- لا تدّعِ إعادة الإنتاج دون تشغيل فعلي ومخرجات تثبته.
- لا تستخدم بيانات إنتاج حقيقية أو بيانات شخصية؛ أنشئ مدخلات مجهولة تعيد الخطأ.
- لا تُخفِ أن الخطأ متقطع إن كان كذلك؛ اذكر نسبة النجاح من تشغيلات فعلية.
- لا تكتب اختباراً يعتمد على تفصيل داخلي سيتغير مع الإصلاح.

## قائمة تحقق
- الاختبار يفشل قبل الإصلاح ولسبب الخطأ نفسه.
- الحد الأدنى للمدخلات موثّق.
- اسم الاختبار يصف السلوك الخاطئ المصحَّح.

## حالات حدّية
- خطأ سباق (race condition): كرّر التشغيل أو أدخل تأخيراً مقصوداً في الاختبار لإظهاره.
- خطأ يظهر في الإنتاج فقط: اطلب إعدادات البيئة وأضف تسجيلاً مؤقتاً بدل التخمين.
- خطأ يعتمد على بيانات قديمة: صمّم مجموعة بيانات اصطناعية تعيد شكلها.
- بلاغ لا يصف المتوقع: اسأل عنه قبل الحكم أنه خطأ.

## مثال كامل
### المدخل
«بلاغ: الصفحة الأولى في قائمة المنتجات تبدأ من العنصر الثالث (الصفحات تبدأ من 1، وحجم الصفحة 2).»

### المخرج
```
# إعادة إنتاج: الصفحة 1 تتخطى العناصر الأولى
البيئة: Node، دالة paginate(items, page, size)
الخطوات: 1) paginate([1,2,3,4,5], 1, 2)  2) فحص الناتج
الفعلي: [3,4]   المتوقع: [1,2]
الحد الأدنى: قائمة من 5 عناصر، page=1، size=2
```
```ts
it("returns the first items for page 1 (pages are 1-based)", () => {
  expect(paginate([1, 2, 3, 4, 5], 1, 2)).toEqual([1, 2]);
});
```
مخرجات التشغيل: `FAIL ... expected [3,4] to equal [1,2]` (فشل لسبب الخطأ المقصود، وقد شُغّلت الدالة فعلاً للتحقق من الناتج `[3,4]`).
فرضية السبب: الدالة تستعمل `page * size` كبداية القطع، وهذا يفترض ترقيماً يبدأ من 0 بينما الواجهة ترسل ترقيماً يبدأ من 1. التالي: إصلاح بعد موافقتك (`(page - 1) * size`) مع تحديد نطاق `page >= 1`.
