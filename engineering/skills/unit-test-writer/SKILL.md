# كتابة اختبارات الوحدة

## متى تُستخدم
- إضافة اختبارات لدالة أو صنف جديد أو غير مغطى.
- تغطية حالات حدّية أو أخطاء مفقودة في اختبارات قائمة.
- تحويل خلل مُكتشف إلى اختبار انحدار (للتفصيل في إعادة الإنتاج استخدم `bug-reproduction`).

لا تُستخدم عندما: المطلوب اختبار تدفق كامل عبر الواجهة (`e2e-test-plan`)، أو إثبات خطأ محدد قبل إصلاحه (`bug-reproduction`).

## خطوات العمل
1. اقرأ الشيفرة المستهدفة وعقدها العام: المدخلات، المخرجات، الأخطاء المُلقاة، الآثار الجانبية، الاعتماديات.
2. اقرأ اختبارات المشروع الحالية لتعرف إطار الاختبار (Jest، Vitest، pytest، JUnit…) وأسلوب التسمية والتنظيم والـ mocks، والتزم به.
3. سرد الحالات: الطبيعية (المسار السعيد)، الحدّية (فارغ، صفر، أقصى/أدنى، حدود الفئات)، والأخطاء (مدخل غير صالح، فشل اعتمادية).
4. اختبر السلوك الظاهر لا التنفيذ الداخلي: لا تتحقق من استدعاء دوال خاصة أو ترتيب داخلي ما لم يكن جزءاً من العقد.
5. اتبع بنية Arrange / Act / Assert، وحالة واحدة منطقية لكل اختبار، واسم يصف السلوك المتوقع (`returns_zero_for_empty_cart`).
6. استخدم بدائل (mocks/stubs/fakes) للحدود الخارجية فقط (شبكة، وقت، عشوائية، ملفات)، وفضّل Fake بسيطاً على Mock كثير التوقعات.
7. اجعل الاختبارات حتمية: لا اعتماد على الوقت الحقيقي أو الترتيب أو بيانات مشتركة بين الاختبارات.
8. شغّل الاختبارات وتأكد أنها تمر، ثم عطّل السلوك مؤقتاً (أو اعكس شرطاً) لتتأكد أن الاختبار يفشل فعلاً حين يتعطل المنطق.

## صيغة المخرجات
ملف أو ملفات الاختبار بالإطار المعتمد، وقائمة الحالات المغطاة، ونتيجة التشغيل، وما لم يُغطَّ ولماذا.

## قواعد وحدود
- لا تغيّر الشيفرة المختبَرة لتسهيل الاختبار إلا بموافقة، واذكر ذلك.
- لا تكتب اختباراً يمرّ دائماً (بلا تأكيدات حقيقية).
- لا تضع بيانات حقيقية أو أسراراً في بيانات الاختبار.
- لا تعتمد على نتائج اختبارات أخرى.
- لا تختلق سلوكاً غير موثّق؛ إن كان العقد غامضاً فاسأل أو وثّق الافتراض.

## قائمة تحقق
- كل فرع شرطي مهم له حالة.
- كل خطأ مُلقى له اختبار.
- الأسماء تصف السلوك لا الدالة.
- الاختبار يفشل حين نكسر المنطق عمداً.

## حالات حدّية
- دالة تعتمد على الوقت: احقن ساعة وهمية.
- دالة غير نقية يصعب عزلها: اقترح فصل المنطق عن الاعتمادية بدل mock ثقيل.
- كود غير متزامن: انتظر النتيجة صراحة واختبر الرفض أيضاً.
- مدخلات عربية/يونيكود: أضف حالة نص بحروف عربية ولاتينية إن كانت الدالة تعالج نصوصاً.

## مثال كامل
### المدخل
```ts
export function applyDiscount(price: number, percent: number): number {
  if (price < 0 || percent < 0 || percent > 100) throw new RangeError("invalid input");
  return Math.round(price * (1 - percent / 100) * 100) / 100;
}
```
### المخرج
```ts
import { describe, it, expect } from "vitest";
import { applyDiscount } from "./discount";

describe("applyDiscount", () => {
  it("reduces the price by the given percent", () => {
    expect(applyDiscount(200, 10)).toBe(180);
  });
  it("returns the same price for 0 percent", () => {
    expect(applyDiscount(99.99, 0)).toBe(99.99);
  });
  it("returns 0 for 100 percent", () => {
    expect(applyDiscount(50, 100)).toBe(0);
  });
  it("rounds to two decimals", () => {
    expect(applyDiscount(10, 33)).toBe(6.7);
  });
  it.each([[-1, 10], [10, -1], [10, 101]])("throws RangeError for (%s, %s)", (p, d) => {
    expect(() => applyDiscount(p, d)).toThrow(RangeError);
  });
});
```
الحالات المغطاة: طبيعية، حدّية (0 و100)، تقريب، أخطاء. لم يُغطَّ: قيم `NaN`/`Infinity` (العقد لا يحددها؛ سؤال: هل تُرفض؟).
