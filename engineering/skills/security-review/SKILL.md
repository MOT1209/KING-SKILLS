# مراجعة أمنية

## متى تُستخدم
- مراجعة أمنية قبل الدمج أو الإطلاق لكود يعالج مدخلات خارجية أو مصادقة أو بيانات حساسة.
- فحص مستودع بحثاً عن أسرار مكشوفة أو أنماط خطرة.
- التحقق من صلاحيات نقاط API.

لا تُستخدم عندما: المطلوب مراجعة عامة للكود (`code-review`) أو مراجعة طلب دمج كامل (`pr-review`).

## خطوات العمل
1. حدّد النطاق وسطح الهجوم: نقاط الدخول (HTTP، رسائل، ملفات)، مصادر البيانات غير الموثوقة، الأصول الحساسة.
2. فحص الحقن: بناء استعلامات SQL أو أوامر نظام أو مسارات ملفات بدمج نصوص من المستخدم. الإصلاح: استعلامات مُعاملة (parameterized)، قوائم سماح، تجنّب تنفيذ الأوامر عبر صدفة.
3. فحص XSS: إدخال بيانات المستخدم في HTML بلا ترميز أو استخدام `innerHTML`/`dangerouslySetInnerHTML`. الإصلاح: ترميز المخرجات حسب السياق، تعقيم موثوق عند الحاجة، سياسة أمان المحتوى (CSP).
4. فحص الأسرار: مفاتيح وكلمات مرور ورموز في الكود أو السجلات أو ملفات الإعداد المُلتزَم بها أو تاريخ git. الإصلاح: متغيرات بيئة أو مدير أسرار، وتدوير أي سر انكشف.
5. فحص التحكم بالوصول: التحقق من الهوية والصلاحية في كل نقطة وعلى كل مورد (لا الاكتفاء بإخفاء الأزرار)، ومنع الوصول لموارد الغير عبر تغيير المعرّف (IDOR).
6. فحص المصادقة والجلسات: تخزين كلمات المرور بخوارزمية تجزئة مخصصة وبطيئة، سلامة الرموز، انتهاء الجلسات، حماية CSRF حيث تلزم.
7. فحص الاعتماديات والإعدادات: إصدارات بثغرات معروفة (أداة فحص الاعتماديات)، CORS واسع، أوضاع تصحيح مفعّلة في الإنتاج، رسائل أخطاء مسرِّبة.
8. صنّف النتائج وفق أسماء فئات معروفة مثل OWASP Top 10 (تحقق من الإصدار الحالي لقائمتها) أو CWE، ورتّبها بالخطورة والاستغلالية.

## صيغة المخرجات
لكل نتيجة: الموقع (ملف:سطر)، الفئة (OWASP/CWE)، الخطورة، الوصف والأثر، الإصلاح المقترح بمقتطف كود، ثم ملخص وما لم يُفحص.

## قواعد وحدود
- اكتفِ بالكشف والإصلاح؛ لا تكتب شيفرة استغلال (exploit) أو حمولات هجوم جاهزة.
- لا تعرض قيمة سر مكتشف كاملة في التقرير؛ اعرض موضعه وأخفِ القيمة، وأوصِ بالتدوير.
- لا تدّعِ أن الكود «آمن»؛ اذكر ما فُحص وما لم يُفحص.
- لا تفحص أنظمة لا يملك المستخدم تفويضاً بفحصها.
- لا تنفّذ الكود المشتبه به.

## قائمة تحقق
- كل مدخل خارجي له مسار تحقق وترميز.
- لا أسرار في الشيفرة أو السجلات.
- كل نقطة حساسة تتحقق من الصلاحية على المورد نفسه.

## حالات حدّية
- سر ظهر في تاريخ git: إزالته من الملف لا تكفي؛ أوصِ بالتدوير ثم تنظيف التاريخ بقرار المالك.
- مكتبة تعقيم/تحقق تتولى الحماية: تحقق من أنها مستعملة فعلاً في كل المسارات.
- إشارات إيجابية كاذبة: وضّح لماذا لا يوجد مسار فعلي من مدخل خارجي إلى الموضع.

## مثال كامل
### المدخل
```js
app.get("/users", (req, res) => {
  db.query("SELECT * FROM users WHERE name = '" + req.query.name + "'", (e, rows) => res.json(rows));
});
```
### المخرج
- الموقع: `server.js:2`
- الفئة: حقن SQL (OWASP Top 10: فئة Injection؛ CWE-89)
- الخطورة: عالية
- الأثر: مدخل `name` يُدمج مباشرة في الاستعلام فيتحكم المهاجم ببنيته.
- الإصلاح:
```js
db.query("SELECT id, name FROM users WHERE name = ?", [req.query.name], (e, rows) => res.json(rows));
```
- ملاحظة إضافية: صيغة العنصر النائب `?` تتبع مشغّل قاعدة البيانات المستخدم (قد تكون `$1` مثلاً). و`SELECT *` قد يعيد حقولاً حساسة؛ حدّد الأعمدة. لم يُفحص: المصادقة على هذه النقطة (غير ظاهرة في المقتطف).
